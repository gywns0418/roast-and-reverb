# 실제 커피 기록의 앱 반영

확인일: 2026-10-13. 사용자가 허용한 원본은 `../coffe_brew_log`이며 원본 파일을 변경하지 않는다.

## 기준과 확인 결과

`coffee_brew_log.md`는 기록 템플릿과 최신 운영 규칙, `beans.md`는 원두 정보, `logs/*.md`는 실제 잔별 관찰이다. `monthly_pick_recommender/taste_profile.json`은 2026-09에 정리한 추천용 추정 규칙이다.

날짜별 Markdown 57개를 실제 파서로 검사했으며 날짜·원두명 필수 확인은 57개 모두 통과했다. 이는 모든 항목이 완전하다는 뜻이 아니다. 실제 추출량을 읽을 수 있던 기록은 26개이며 나머지는 미기록을 유지한다. 개인 원본이나 전체 로그를 공개 저장소의 시드 데이터로 복사하지 않았다.

## 의미를 보존하는 규칙

- 부은 물 총량과 서버/컵에 실제 내려온 양은 별개다. `16g / 245g`은 원두 대 부은 물 비율이며, 추출량이나 TDS가 아니다.
- `45 + 100 + 100`은 개별 푸어량, `45 → 145 → 245`는 누적값이다. 둘의 총 물량은 245g이다. `6888`처럼 압축된 표기는 새 UI에서 임의 해석하지 않는다.
- 분쇄도 문자열은 그대로 저장한다. C3 ESP의 30클릭/바퀴는 사용자의 장비 기록 규칙이며 다른 그라인더에 적용하지 않는다. 청소 후 0점 변화도 가능하므로 클릭 수만으로 원인을 확정하지 않는다.
- 날짜는 문서의 명시값, 없으면 날짜별 파일명을 사용한다. 시간이 없으면 현재 시각을 채우지 않는다. 날짜가 유효하지 않으면 가져오기 대상으로 선택하지 않는다.
- 맛을 숫자로 평가하지 않은 잔은 숫자 0이나 3으로 대체하지 않는다. '부드러운 단맛' 같은 표현은 원문 텍스트로 남긴다.
- 기록에 없는 음악은 만들지 않는다. 커피를 가져온 뒤 실제 곡을 사용자가 골라 페어링한다.
- 재고 가격과 잔량 자동 차감은 추가하지 않는다. 소진 처리는 사용자가 알려줄 때만 한다. `beans.md` 상단의 예전 잔량 안내보다 `coffee_brew_log.md`의 최신 관리 규칙이 우선이다.
- 관찰 사실, 가능한 해석, 다음 실험은 구분한다. 한 잔에서 바꿀 변수는 원칙적으로 하나다. 결과가 좋으면 동일 조건 재현과 누락 측정값 확보가 먼저다.

## 적용된 데이터 구조

기존 `coffee_log` 컬럼을 유지하고 `brew_details` TEXT 컬럼을 추가했다. 기존 DB는 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`로 보존한다. 이 문법과 운영 구성은 현재 H2 기준이다. 다른 DB로 이전할 때 별도 마이그레이션을 준비한다.

| 원본 항목 | 앱/API 항목 | 처리 |
| --- | --- | --- |
| 날짜, 이름, 로스터리, 원산지, 가공 방식 | `drinkDate`, `beanName`, `roastery`, `originCountry`, `process` | 명시값 보존 |
| 물 온도, 분쇄도, 총 추출 시간 | `waterTemp`, `grindSize`, `brewTime` | 정확한 시간만 초로 변환, 불명확한 표기는 원문 유지 |
| 원두량, 부은 물, 실제 내려온 양 | `brewDetails.doseGrams/waterGrams/beverageGrams` | g 단위, 미기록은 null |
| 시, 드리퍼, 필터, 그라인더 | `recordedHour`, `dripper`, `filter`, `grinder` | 추정해서 채우지 않음 |
| 로스팅·개봉 날짜, 푸어량 | `roastDate`, `openedDate`, `pourText`, `pourMode` | 개별/누적 구분 |
| 후미, 식으면서, 만족도, 재음용 | `aftertaste`, `coolingNotes`, `ratingText`, `wouldRepeat` | 원문 텍스트 |
| 관찰·해석·다음 실험 | `sensoryNotes`, `analysisNotes`, `nextExperiment`, `recipeText` | 원문 보존 |
| 가져온 파일 | `sourceFile`, `sourceFingerprint` | 파일명과 SHA-256, 원본 본문 전체를 시드에 포함하지 않음 |

`brewDetails`는 API 쓰기 시 JSON 객체를 받으며 DB에는 JSON 문자열로 저장한다. 읽기 응답의 `brew_details` 문자열은 프론트 어댑터가 객체로 변환한다. 서버는 수량·시간·JSON 크기를 검증한다. 부분 수정에서 전달하지 않은 측정값은 기존 값을 보존한다.

## 사용자 흐름

커피 로그 → **Markdown 기록 가져오기** → `logs`의 파일을 선택 → 원두·날짜·비율과 가져오기 가능 여부를 확인 → 선택한 기록 저장. 한 번에 100개까지 확인한다. 중복 검사는 현재 조회하는 최대 1,000개 기록의 파일 내용 해시 기준이며 서버 차원의 동시성/전역 중복 방지 기능은 아니다.

추출 조건을 새로 쓸 때는 **16g · 245g 기준 레시피 채우기**를 선택적으로 사용할 수 있다. 이는 최근 개인 기록을 재현하기 위한 입력 도우미이며, 이미 측정된 사실이나 모든 원두의 권장 레시피로 취급하지 않는다. 실제 내려온 양·시간은 자동으로 채우지 않는다.

## 월픽 관련 주의

기존 `generate_seed_sql.py`는 원본 checkout의 `data.sql` 전체를 덮어쓸 수 있다. 이번 작업에서는 실행하지 않았다. 다음 수정 시 출력 파일을 분리하거나 자기 마커 구간만 갱신하도록 바꾼다. 회원·커피·음악·페어링 시드와 운영 DB를 통째로 덮어쓰지 않는다.

취향 JSON의 다크/디카페인 제외는 소유자 선호이고, 발효 가공 감점은 추정 신호다. 10월 기록에는 콜드룸 내추럴에 대한 긍정적 관찰도 있어 가공명만으로 불호를 단정하면 안 된다. 월픽 점수와 음악 페어링 점수는 서로 다른 척도다.
